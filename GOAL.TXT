RustAssetRipper Product Convergence
==================================

Objective
---------
Continue the full Rust port and acceptance work defined by the project's `AGENTS.md` and the user's Product Convergence task. The current local AssetRipper source snapshot is the authoritative behavior baseline. The delivered product core must be Rust-owned; it must not delegate parsing, object construction, reference resolution, resource restoration, scene/Prefab/animation handling, or export to AssetRipper, UABEA, C# DLLs, or .NET processes.

Do not declare completion until the full in-scope product surface is implemented and validated, the Rust product builds and runs independently, every authorized VRChat sample has a traceable final result, correctness-critical differences are resolved, and required regressions and hand-off documentation are complete. Any required behavior or check that is unimplemented, failed, externally blocked, or not run keeps the overall goal open.

Execution discipline (mandatory)
-------------------------------
1. **Work one concrete blocker at a time.** Reproduce it, identify affected input objects and source behavior, establish expected semantics, make one generic fix, run focused and affected tests, rebuild the actual product, replay the same real input into a fresh output directory, compare the affected semantics and previously fixed slices, record evidence, then commit coherent progress before taking the next blocker.
2. **Investigate before editing.** Trace each difference through input bytes/SerializedFile fields, source implementation or TypeTree, Rust decoding/routing, references, and output representation. Class IDs, versions, file scope, PathID/local fileID, field order, array order, and external references matter. Do not infer correctness from names, counts, folder sizes, or one reference tool's output.
3. **Use evidence-backed normalization only.** Pair documents by stable identity such as source file, class ID, and local fileID. Normalize an output GUID only after both projects' `.meta` files resolve it to the same relative asset path. Keep array order, curve tangents, bindings, LOD membership, renderer references, and runtime-relevant values intact. Do not widen numeric tolerances after seeing a difference.
4. **Never turn a partial check into a pass.** A passing unit test does not prove product behavior. A successful CLI exit or generated file does not prove semantic correctness. A check not actually run must be recorded as “not run”; a failed command must retain its real exit code and cause. Keep static validation separate from Unity import/runtime validation.
5. **Do not hide unsupported or failed data.** No sample-name/hash/PathID special cases; no skipped resources, dropped fields, null substitution for unresolved references, default/zero replacement, raw-byte dump as a substitute for structured export, relaxed assertions, or deleted failing tests to make a report green.
6. **Treat comparison tools as evidence, not truth.** Investigate Rust/source/UABEA differences against original bytes, format rules, stable object identities, and actual exported references. Two tools failing alike does not establish that Rust may omit support.
7. **Protect the workspace.** At each continuation, read this file, `docs/next-agent-handoff.md`, the latest relevant `docs/validation-log.md` entry, and `git status`. Preserve user edits and untracked files. Never alter/move/delete original bundles, frozen source, or UABEA. Never run destructive reset/clean or force-push commands. Stage explicit paths only.
8. **Keep the hand-off truthful and actionable.** Record source symbol, Rust location, exact command, exit code, input identity, fresh output path, semantic result, limitations, and the single next blocker. Update the difference log, validation log, continuation notes, and hand-off when a blocker changes state. Never write expected or inferred results as executed results.
9. **Commit only coherent, reviewed progress.** Before commit, inspect the diff and staged file list; run relevant checks; verify user-owned scratch is excluded. Use a normal push only, then compare local HEAD with `origin/main`. If push fails, diagnose it without force. If the user explicitly requests a checkpoint before a required build or real-sample replay, commit only with the missing validation clearly marked pending and exact next steps recorded; never describe that implementation as resolved.
10. **Continue autonomously.** Do not stop after each small fix to ask whether to continue. Ask only when missing user data, authorization, or an external-state change genuinely prevents progress; continue independent work meanwhile.
